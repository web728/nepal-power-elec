pages render — you're only configuring things to move from "demo mode" to "live with a real database and
email, on the final domain."

file is the ordered checklist to get from this folder to a deployed, publicly launched site, followed by

## Architecture Reference

### Full architecture

Next.js 16 App Router, server-rendered/statically-generated by default. Pages live under `src/app/`;
each folder is a URL segment with its own `page.tsx` and `metadata` export. Six `POST`-only API route
handlers under `src/app/api/*/route.ts` accept form submissions, validate them server-side with Zod
(never trusting client-side validation alone), rate-limit by IP, persist to Supabase (or log to console
if Supabase isn't configured), and send transactional email via Resend (or log if not configured). A
lightweight admin CMS (`/admin`) is gated by Supabase Auth + a role check and reads the six submission
tables through a generic module viewer. No separate backend service exists — the API routes *are* the
backend, running as Node.js/serverless functions wherever this is deployed.

### Database structure

See `supabase/schema.sql` for the authoritative DDL. Summary: a `profiles` table (id, full_name, role
enum, organizer, created_at) drives admin access control, plus six submission tables — one per form (see
`docs/FORM_TABLE.md` for exact field-to-column mapping) — each with `id`, `reference_number` (unique),
`created_at`, and its form-specific columns. Every table has Row Level Security enabled; there are no
public INSERT or SELECT policies (all writes/reads happen server-side via the service-role key), plus one
admin-only SELECT policy per table via an `is_admin()` SQL helper, for any future direct-authenticated-
client reads.

### Forms and routing

All 6 forms follow the same pattern: client component (`src/components/forms/*.tsx`) validates with the
shared Zod schema, `fetch()`s its API route, shows an inline confirmation or error state. Each API route
(`src/app/api/*/route.ts`) re-validates server-side, rate-limits by IP+route, calls `submitLead()` to
persist + generate a reference number, then sends email. Full field lists, validation, and state behavior
are in **`docs/FORM_TABLE.md`**.

### Email routing

`src/lib/email/send.ts` wraps Resend; `src/lib/email/templates.ts` holds the verbatim approved
confirmation copy for each form. Every API route sends two kinds of email: an **acknowledgement** to the
submitter, and a **notification copy to all three organizers** (never just one — see "Organizer contact
routing" below). Without `RESEND_API_KEY` configured, both are logged to the server console instead of
sent, so the full flow is verifiable before email is connected.

### Organizer contact routing

All three organizers' emails/phones live in exactly one place — the `organizers` array in
`src/lib/site-config.ts`. Every place that needs to "contact the organizers" (footer, Organizers page,
Contact page, every form's notification fan-out) reads from that same array, so no organizer can end up
missing from a notification list or visually deprioritized relative to the others — this was a
non-negotiable requirement in the build brief ("equal prominence").

### CMS roles

Defined in the `user_role` Postgres enum (`supabase/schema.sql`) and mirrored in `src/lib/auth.ts`:
`super_admin`, `editor`, `contributor`, `media_manager`, `form_viewer`. All five currently grant access to
`/admin` (see `isAdminRole()`); differentiating their *permissions* within the admin UI (e.g. contributor
can't publish) is a documented next step for when the admin CMS grows beyond its current read-oriented
v1 scope.

### Security measures

Zod server-side validation on every form endpoint · per-IP rate limiting (5 requests/60s/route) ·
content-based duplicate-submission guard (2-minute window) · RLS enabled on every Supabase table with no
public read/write policies · service-role key never exposed to the browser · secrets excluded from the
repository via `.gitignore` (and confirmed absent via a full scan — `docs/SECURITY_REMEDIATION_REPORT.md`)
· cookie-consent gating for all non-essential scripts · security headers (CSP/HSTS/X-Frame-Options/
X-Content-Type-Options/Referrer-Policy/Permissions-Policy) applied via `next.config.ts`, curl-verified.
`npm audit` shows 0 findings in any production-relevant package (`next`/`sharp`/`postcss` fully
remediated) — see `docs/SECURITY_REMEDIATION_REPORT.md` for the 9 remaining dev-only ESLint-toolchain
findings and why they're an accepted risk. Still deferred to the hosting/deployment layer: HTTPS itself
(headers are ready, but need a real TLS-terminating host), MFA on hosting/Supabase accounts, a WAF.

### Backup procedure

Once Supabase is connected: enable automated daily database backups (Supabase dashboard → Database →
Backups), retain at least 30 days of restore points, and test the restore process at least once before
go-live and quarterly thereafter (per `LAUNCH_CHECKLIST.md`). Keep the source code itself backed up
beyond a single machine (a Git remote — see the repository link provided at handover — already serves
this purpose).

### Deployment procedure

See Sections 1–5 below for the step-by-step version. In short: `npm install && npm run build` must pass
(it does, see `docs/FINAL_AUDIT_REPORT.md`), then deploy to Vercel or any Node host, set the environment
variables from `ENVIRONMENT_SETUP.md`, and point DNS at it.

### Maintenance instructions

- Keep `next`, `sharp`, and `postcss` updated (currently `npm audit`-clean — see
  `docs/SECURITY_REMEDIATION_REPORT.md`); re-run `npm audit` after any dependency bump and before each
  major content refresh. Periodically retry the `eslint@10` upgrade (documented as blocked by an
  `eslint-config-next` incompatibility) once a compatible release ships.
- Re-run `npm run build`, `npm run lint`, and `npm test` after any code change, before deploying.
- Content edits (copy, FAQs, stats, organizer contacts) don't require a rebuild step beyond
  `npm run build`/`next dev` picking up the change — see `CONTENT_ADMIN_GUIDE.md`.
- Review `LAUNCH_CHECKLIST.md` in full again after any structural change (new page, new form, new nav
  item) — several of its items (sitemap, structured data, accessibility) can regress silently.

## 1. Install & run locally

```bash
npm install
npm run dev
```

Open the printed localhost URL. Click around — forms submit successfully and log to your terminal (no
database needed yet). **Node.js 20+** required.

## 2. Set environment variables (all optional, see table in README)

```bash
cp .env.example .env.local
```

## 3. Connect Supabase (recommended before going live)

1. Create a project at [supabase.com](https://supabase.com).
2. Run `supabase/schema.sql` in the Supabase SQL editor.
3. Copy the Project URL / anon key / service role key into `.env.local`.
4. Create an admin account, then set that user's `profiles.role` to `super_admin` to unlock `/admin`.

## 4. Connect email (Resend)

1. Create an account at [resend.com](https://resend.com), verify a sending domain.
2. Add `RESEND_API_KEY` and `EMAIL_FROM_ADDRESS` to your hosting provider's environment variables.

## 5. Deploy

**Vercel (recommended, zero config):** push this repo to GitHub → import into Vercel → add the env vars
under Project Settings → Environment Variables → Deploy.

**Any other Node host:**
```bash
npm run build
npm run start
```

## 6. Before announcing the site is live — final launch checklist

This mirrors the approved Design Specification's own Section 17 "Final Launch Checklist":

- [ ] Set `NEXT_PUBLIC_SITE_URL` to the production domain in `.env.local` / hosting env vars (defaults to
      `https://www.nepalpowerelec.com` in `src/lib/site-config.ts`).
- [ ] Run `supabase/schema.sql` against the production Supabase project.
- [ ] Set a real `RESEND_API_KEY` and verify the sending domain (SPF/DKIM/DMARC — see design spec §8.4).
- [ ] Confirm all three organizers have shared, documented access to: the domain/DNS, hosting account,
      Supabase project, Resend account, analytics, and Search Console. No single organizer should be the
      sole holder of any credential (per the spec's "equal organizer governance" rule).
- [x] Real favicon/app icons — **done**: `favicon.ico`, `icon-16/32/48.png`, `apple-touch-icon.png`, and
      Android/PWA icons (including a maskable variant) were generated from the approved primary event
      logo's own icon glyph, cropped (not redrawn) — see `docs/FINAL_RELEASE_NOTES.md`.
- [ ] Set analytics IDs (`NEXT_PUBLIC_GA_MEASUREMENT_ID`, `NEXT_PUBLIC_GTM_ID`, etc.) if required at
      launch — they only load after a visitor accepts analytics cookies.
- [ ] Test all 6 forms end-to-end against the real Supabase + Resend configuration (not just demo mode).
- [ ] Confirm production `robots.txt`/`sitemap.xml` are reachable and that `/admin`, `/dashboard`,
      `/login`, `/search` remain `noindex`.
- [ ] Validate Event/Organization/Breadcrumb/FAQ structured data with Google's Rich Results Test.
- [ ] Run a Lighthouse pass against the deployed URL (Core Web Vitals targets: LCP ≤2.5s, INP ≤200ms,
      CLS ≤0.10 at the 75th percentile, per the design spec).
- [ ] Keyboard-only and screen-reader (NVDA+Chrome or VoiceOver+Safari) smoke test of the homepage,
      Book a Stand, Register to Visit, and the FAQ accordions.
- [ ] Populate real exhibitor data **only once bookings are confirmed** — there is deliberately no
      exhibitor directory or "Exhibitors" nav item yet (see FILE_INVENTORY.md).
- [ ] Replace the "not yet configured" `/login`/`/dashboard` shells with real participant-facing features
      only if/when that scope is actually commissioned — they are intentionally minimal today.

## What's NOT included in this package

- `node_modules/` — regenerated by `npm install`.
- `.next/` — regenerated by `npm run build`.
- Any `.env.local` — create this from `.env.example` with real credentials.
- A hosting account, domain registration, Supabase project, or Resend account — these require the
  organizers' own accounts and payment details, which this build process has no access to. See
  "Third-Party Services" in `docs/FINAL_AUDIT_REPORT.md` for what's needed and roughly what each costs.

## Questions about content/scope

This site's content is intentionally scoped to only what's in the official 2026 brochure, the 2025
post-show report, and the two approved build-specification documents — no invented exhibitor directory,
no fabricated stand pricing, no fake co-located shows. See `docs/FILE_INVENTORY.md` (the full source
audit and conflict log) and `docs/FINAL_AUDIT_REPORT.md` (omitted items + decisions made) before adding
new pages or "coming soon" sections.
